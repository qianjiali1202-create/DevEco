IDE 字号、行高与组件尺度

把文字的大小、行框的高度和控件的边界，放回同一个设计系统里。

研究结论

先定文字层级，再定容器；圆角按组件角色区分。

从目前能追溯的 IJ 和 VS Code 数据看，密集工作台可以从 13 px UI 字号出发。行高和容器高度应独立配置：IJ 本库的 13 / 16 文本放在 24 px 表格行或 28 px 按钮中；这些是不同对象，不是一套通用“行高”。[S01–S07]

对设计决策的影响

  1. 不要把编辑器参数套到 UI。

    代码、导航列表、表单、长段落有不同阅读任务，分别建立 token。

  2. 放大文字时同步检查垂直余量。

    字号升到 16，不能只改 font-size；需要同时检查行框、行容器及中文回退字形。

  3. 圆角表达组件层级。

    本库按钮 / 输入框 R4，弹窗 R8，复选框边框 R3；页签指示条 R2。

建议起点 · 待用户验证

默认沿用 IJ；中文阅读场景提供更舒展的密度。

标准 13 / 16 → 可读 14 / 20 → 大字 16 / 24。组件高度随方案调整，避免全局盲目放大。

值得带回方案的三个观察

13 是参考起点

IJ 的 UI 默认与 VS 基础字号相近；仅这两个样本不足以推出“所有 IDE 都用 13”。Xcode 的 13pt 平台参考也不能直接并入 px 统计。

同字号可以有不同密度

VS 基础行高 18.2 与 IJ 组件行框 16 来自不同实现。真实密度还取决于容器、padding、是否换行与字号缩放。

可配置性影响采样

编辑器、终端、AI 阅读区需要分别记录。用户导入配置后的页面，不能被当作出厂默认界面。

C · 方案 / 待测

14/20、16/24、增大的行与控件高度是方案参数。没有本机测量的竞品不提供虚构精确值。

下一轮验证怎么做

  1. 记录环境：产品版本与构建号、操作系统、浅色主题、UI 缩放、编辑器缩放、显示器倍率、字体回退与是否导入设置。
  2. 固定样本：同一中英文项目名、长路径、三层目录、相同代码与 336 px 列表视口；分别记录 UI、编辑器、终端和 AI 阅读区。
  3. 测量边界：字体设置值、文字行框、容器矩形、可见边框、点击命中区域分别记录。原生 pt 与物理截图像素先校准，不直接换算。
  4. 验证体验：让开发者完成定位设置、阅读说明、选择列表项等任务；记录截断、误点、定位时间与主观舒适度。当前仅完成原型布局与交互验证，不声称效率提升。
