# 仓库提交与发布

目标是把已经完成并验证的改动安全地提交到目标仓库，并确认最终链接可访问。

## 开始前

1. 读取仓库级说明文件、当前分支、远端 HEAD、工作区状态和现有发布配置。
2. 明确本次提交包含哪些文件，保留用户和其他协作者的无关改动。
3. 在提交前完成与改动相称的语法、交互和视觉检查。
4. 目标为本仓库 DevEco 时，读取 [references/deveco-pages.md](references/deveco-pages.md)。

## 提交身份

- 不复制其他仓库作者的姓名、邮箱、签名配置或 AI 署名规则。
- 优先使用已认证的 GitHub 连接提交，使作者身份来自当前连接账号。
- 使用本地 Git 时，先检查仓库级 `user.name` 和 `user.email`。只有已经知道仓库主人的有效身份时才修正配置，并仅写入当前仓库。
- 提交后核对 commit author、目标分支和文件列表。不要在提交信息中添加工具生成的共同作者尾注。

## 提交与推送

- 提交信息描述最终行为和解决的问题，避免只罗列文件名。
- 推送前重新读取远端 HEAD。使用 fast-forward 或带 expected SHA 的更新，远端已变化时先检查差异。
- 不使用强制推送，除非用户明确要求且已经评估影响。
- 不覆盖未提交的本地改动，不用 reset 或清理命令绕过冲突。

## GitHub Pages

- 先确认现有 Source 是分支目录还是 Actions。保留现有发布方式和稳定 URL。
- 已经有 workflow 时更新原 workflow；不要创建第二套竞争发布流程。
- 从分支目录发布时，直接更新该分支和目录，不擅自切换成 Actions。
- 保留已经对外分享的路径；确需迁移时保留别名或重定向。
- Pages 根地址可访问并不代表新页面可访问，要验证本次交付的具体 URL。

## 完成标准

- 远端分支指向新 commit，作者和提交内容正确。
- 必需检查通过，没有遗漏资源或错误相对路径。
- 线上具体页面返回成功，并能识别本次版本；部署尚在运行时如实说明状态。
- 最终回复给出仓库、分支、commit 链接、页面链接和验证结果。
